## Privacy, uploads (F005, F006, F007, F009)

- **R01 opaque image keys.** Object key = `kudo-images/{uploadId}.{ext}` where `uploadId` is a random UUID. No user id in any key, URL, DTO, HTML or filename. Ownership lives only in server-side table `kudo_uploads(id uuid pk, owner_id → users, object_path unique, mime, size_bytes, created_at, kudo_id null → kudos, attached_at null)` owned by F005. Anonymous kudo DTOs (board, detail, profile lists, notifications) contain no stable author identifier. Test: anonymous kudo with images read by a third user — inspect every field and URL.
- **R02 anonymity edits vs notifications.** When `PATCH /api/v1/kudos/{id}` turns `is_anonymous` on, the same Go transaction redacts sender fields (`senderId`, `senderName`, avatar) from `notifications.params` of every notification with that `kudo_id`. Notification reads additionally re-mask by the kudo's CURRENT `is_anonymous` (join on `kudo_id`) for non-admin viewers, which also covers a create racing the edit. Turning anonymity off does not re-add names to old notices. What a recipient already saw cannot be recalled (stated limitation).
- **R03 real-object validation.** Bucket `kudo-images` is private with bucket-level `file_size_limit` 5 MB and `allowed_mime_types` image/jpeg, image/png, image/webp. Signed upload URLs never allow upsert (keys immutable). On create/edit, Go finalizes each attachment: `uploadId` must exist in `kudo_uploads`, be owned by the caller, be unattached (or already attached to THIS kudo on edit); Go reads the stored object's metadata (size, content-type) from Storage AND sniffs the first 512 bytes (magic number JPEG/PNG/WebP); count 0–5. Any failure → 422 `invalid_attachment`, nothing committed. The client sends `uploadId`s, never paths. Tests: lying MIME/size, missing object, foreign upload, re-use of an attached upload, replace attempt.
- **R04 cleanup contract.** `DELETE /api/v1/uploads/{uploadId}`: caller must own it and it must be unattached → deletes object + row (204); attached → 409. One upload attaches to at most one kudo (`kudo_uploads.kudo_id` set once). During edit: newly uploaded unsaved files are deleted via this endpoint on cancel/remove (best-effort, AD05); committed attachments removed in an edit are detached in the edit transaction and their objects deleted by Go only after commit (best-effort, logged). Orphan unattached uploads older than 24 h may be purged by a manual/admin script (no scheduler required).
- **R15 shared DTOs.** `units` gets column `code text not null unique` (e.g. `CECV2`), seeded with units; profile and card show `unit.code`. F006 technical spec defines the one concrete `KudoCard` DTO: `{ id, createdAt, title, contentHtml, isAnonymous, sender: {id, name, avatarUrl, unitCode, heroTier} | null, receiver: {id, name, avatarUrl, unitCode, heroTier}, hashtags: string[], images: [{url, width?, height?}], heart: {total, viewerHearted, viewerCanHeart}, isOwn, status }`; list responses `{ items: KudoCard[], nextCursor: string|null }` (opaque base64 keyset of `created_at,id`). F007 consumes exactly this. Profile counts failure → `counts: null` plus `countsUnavailable: true` (rest of page still renders).
- **R20 content validation.** Order: sanitize (Go allow-list) → derive canonical visible text (text nodes, whitespace runs collapsed to one space, trimmed; a mention counts as its displayed `@Name`; entities decoded) → required = visible text non-empty; max length = 1,000 Unicode code points of visible text. Validation runs on the stored representation. The frontend mirrors the same metric for its counter. Sanitizer tests: exact 1,000/1,001 boundary, whitespace-only, content that becomes empty after sanitizing, entities, emoji (surrogate pairs = 1), unsafe links/attributes.

## Gamification & moderation (F005, F008, F011, F012)

- **R09 campaign failure.** The authoritative campaign lookup inside the heart transaction failing → transaction rolls back, 500 `campaign_lookup_failed`; the heart is NOT recorded. Weight 1 only when the lookup succeeds and finds no active campaign. The separate `GET /api/v1/campaigns/active` (badge display) failing only hides the badge. Remove any "fall back to weight 1 on error" wording.
- **R10 hero tier transitions.** In the kudo-create transaction Go locks the receiver row (`select … from users where id=$1 for update`), computes the receiver's distinct-real-sender count over public kudos before and after the insert, maps both to tiers; if the tier rose, the transition `{receiverId, fromTier, toTier}` is passed to the post-commit notifier. Dedupe key `hero_level:{receiverId}:{toTier}` (one notice per tier ever). Moderation changes (Spam ↔ Public) never emit level-up notices; tiers are still derived on read. Tests: same sender twice (no change), two simultaneous 5th senders (exactly one notice), spam/restore (no notice).
- **R11 icon-set completion.** `POST /api/v1/me/secret-boxes/open` locks the user row (`for update`) for the whole open, so opens are serialized per user. Go compares the distinct icon set before/after the draw; first time it reaches 6, it sets `users.icons_completed_at` (null → now, set once) in the same transaction and passes a completion event to the notifier (dedupe `icons_completed:{userId}`). Tests: two boxes / two missing icons opened concurrently → exactly one completion; later repeat opens → no second completion.
- **R12 idempotent box opening.** The client generates one `Idempotency-Key` (UUID) per opening intent and sends it as a header; `secret_boxes.open_request_id uuid unique null`. If a box with that key is already opened, Go returns the stored result (same box id, icon, summary) with 200 and consumes nothing. Response `{ boxId, icon, summary: {unopened, opened, distinctIcons} }`. Retry in the UI reuses the same key. Test: commit succeeds, response dropped, retry same key with ≥2 unopened boxes → same result, only one box consumed.
- **R13 moderation versioning.** `kudos.moderation_version int not null default 0`, incremented on every real status change. `POST /api/v1/admin/kudos/{id}/spam|public` body `{ expectedVersion }`; update is `… where id=$1 and moderation_version=$2 and status<>$target`; on version mismatch → 409 `stale_decision` with the current row (status, version, moderatedBy, moderatedAt) so the UI refreshes it; same target and same version → 200 `changed:false`. Tests: opposing stale decisions, Spam → Public → Spam cycle, double click.
- **R05 single role source.** Role always comes from `users.role` via F002's shared auth context and `RequireAdmin` middleware. No `profiles` table anywhere.

## Platform / shell / auth (F001, F002, F003, F004, F010, system)

- **R06 browser transport (system contract, owned by F002).** Go CORS middleware runs BEFORE auth: allowed origins from env `FRONTEND_ORIGINS` (comma list, e.g. `http://localhost:3000`); `OPTIONS` preflight answered 204 without JWT; allowed methods GET, POST, PUT, PATCH, DELETE; allowed headers `Authorization, Content-Type, Idempotency-Key`; exposed headers `Content-Disposition`; credentials not used (bearer token only, no cookies to Go); max-age 600. All browser calls use `Authorization: Bearer <supabase access token>`. No BFF.
- **R07 Next.js layout structure.** Root `app/layout.tsx` = `<html>/<body>`, fonts, locale provider only (no chrome). Route groups: `app/(shell)/layout.tsx` full chrome (header/footer/FAB); `app/(minimal)/layout.tsx` for Login + 403/404 minimal chrome; `app/countdown/` bare; `app/admin/layout.tsx` admin chrome with admin nav (F010 supplies items as a static config imported by that layout). Active link highlighting uses a client `NavLinks` component with `usePathname()`. `/me` (role, name, avatar) is fetched server-side in the (shell) and admin layouts with `cache: 'no-store'`, and the client header re-fetches `/me` on window focus; every admin API call is still enforced by Go. Editors must cite the installed guide `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/layout.md` and `route-groups.md` (read with Read/Grep tools).
- **R08 two countdown modes.** Shared pure `CountdownDisplay` (+ `useCountdown(targetIso, serverNowIso)` arithmetic). `LaunchCountdown` (F003): target `startAt`, redirects to `/` at 0 ms or when resync returns `status: active`. `CeremonyCountdown` (F004): target `ceremonyAt`, never redirects, stops at 00 and shows the post-zero state; ignores `status`. Tests: interval `start_at <= now < ceremony_at`, refocus resync, both zero boundaries.
- **R16 deterministic fixtures.** Seed scenarios in `backend/db/seeds/` selectable by env `SEED_SCENARIO`: `prelaunch` (start_at = now()+2 days, ceremony_at = now()+20 days), `live` default (start_at = now()-1 day, ceremony_at = now()+14 days), `after-ceremony` (start_at = now()-30 days, ceremony_at = now()-1 day). Demo activity (users, kudos, hearts, boxes) dated within the last 14 days so Overview's last-30-days default shows data. AD03's design sample date stays documented as the "production placeholder", not the dev default. Include a sub-minute launch boundary test (start_at = now()+30 s) and the event-unavailable fallback.
- **R17 desktop only.** Release acceptance is desktop: minimum viewport width 1280 px; below that the page keeps its desktop layout with horizontal scroll. Mark every inherited mobile/tablet row (collapsed header, award tabs, breakpoints) "Out of release scope (AD01, R17)" instead of deleting history.
- **R18 Forbidden page.** Per AD15 the admin layout renders a plain Forbidden page; acceptance for that page is visual only (status code not asserted). HTTP 403 acceptance applies to Go endpoints only. Do not enable `experimental.authInterrupts`.
- **R21 auth/database bootstrap (system contract, F002).** Supabase project uses asymmetric JWT signing keys (ES256 or RS256) exposed via JWKS; Go accepts only those algorithms, issuer `${SUPABASE_URL}/auth/v1`, audience `authenticated`, verifies exp/nbf. Supabase Auth: Google provider only (email/password, magic link and other providers disabled). Provisioning requires `email_verified = true`, provider `google`, and email domain `@sun-asterisk.com` (case-insensitive). Go connects as dedicated Postgres role `saa_api` with DML grants on business tables and `BYPASSRLS`; RLS enabled deny-all on every business table; `anon`/`authenticated` have no grants on business tables or the `kudo_heart_state` view. Secrets (DB URL, Storage service key) live only in Go env, never in Next.js.
- **R22 missing-profile recovery.** When Go answers 403 `profile_not_provisioned`, the frontend calls `POST /api/v1/me/provision` once; if that fails, it signs out (clears the Supabase session) and navigates to `/login?error=profile_unavailable`. The proxy does not redirect a signed-in user away from `/login` when an `error` query param is present. F001's `/me` handling names this case.
- **R23 deadlines.** Go HTTP server: ReadHeaderTimeout 5 s, ReadTimeout 15 s, WriteTimeout 30 s; per-request DB context 5 s (exports 20 s). Next.js server-side fetches to Go: 5 s timeout (AbortSignal.timeout). Launch-gate lookup in `proxy.ts`: 1.5 s then fail open. Post-commit notification work runs with its own context of 2 s detached from the request; failure is logged and never changes the successful mutation response.

# Addendum — Codex re-review findings N01–N12 (2026-11-10)

Source: `reports/codex-rereview-specs.md`. User approved fixing them. Same precedence: this addendum overrides earlier text where they differ.

- **N01 late named notification (F005, F009).** Kudo-linked notification creation runs in a short Go transaction that first takes `select is_anonymous from kudos where id=$1 for share`; the F005 edit holds `for update` on the same kudo row, so create and anonymity edit are serialized. If the kudo is anonymous at insert time, sender fields are stripped before storing. Combined with the edit's redaction, no stored row ever carries a sender for a kudo that was anonymous at any time after that row's insert; turning anonymity off never re-adds names. Test sequence: named create → anonymous edit (redaction) → late notice insert → named edit → read: no sender in either notice.
- **N02 upload lifecycle (F005, F006).** `kudo_uploads.state` enum `pending | attached | pending_delete` (replaces relying on `kudo_id` alone). Upload starts `pending`; attaching sets `attached` + `kudo_id`. A "kept" attachment on edit must be `attached` AND still referenced by a current `kudo_images` row of this kudo (checked under the kudo row lock). Removing an attachment in an edit deletes its `kudo_images` row and sets `pending_delete` in the same transaction; `pending_delete` is never eligible again. Post-commit cleanup deletes only `pending_delete` uploads (object then row). The manual purge script handles `pending` older than 24 h and any leftover `pending_delete` rows. Test: two edits from the same stale prefill with cleanup paused between them.
- **N03 once-ever events (F009).** Kinds `hero_level_up` and `icons_completed` use a permanent partial unique index `(recipient_id, dedupe_key) where kind in ('hero_level_up','icons_completed')`; insert uses `on conflict do nothing`, independent of `read_at`. Other kinds keep the unread-merge rule. Test: reach tier → read notice → moderated below tier → reach same tier again → no second notice.
- **N04 hero event mapping (F005 → F009).** Producer of `hero_level_up` is F005 (not F008). F005 passes `{receiverId, fromTier, toTier, sendersCount}` (`sendersCount` = after-count captured under the lock). F009 maps: `params.levelKey = toTier`, `params.fromLevelKey = fromTier`, `params.sendersCount = sendersCount`; dedupe `hero_level:{receiverId}:{toTier}`. Contract test renders the notice in VN and EN.
- **N05 lock order (F005, F011).** Global lock order: kudo row first, then receiver `users` row. F011's status-change transaction locks the kudo row `for update`, then the receiver's `users` row `for update`, then applies the versioned update; it still never emits tier notices. F005 create locks only the receiver row (the new kudo does not exist yet); F005 edit locks only the kudo row (recipient is immutable). Test: barrier-controlled create (repeat sender) vs restore-from-Spam of a fifth sender → no level-up notice from the create.
- **N06 server-render recovery (F001, F002).** When a Server Component layout gets `profile_not_provisioned` and the one reprovision attempt fails, it renders a client `ProfileRecoveryRedirect` component (no chrome) that calls browser `supabase.auth.signOut()`, awaits it, then `location.replace('/login?error=profile_unavailable')`. No new Next route handler. Test: direct protected-page load with valid token, absent profile, failing provision → cookies cleared, Login stable after reload.
- **N07 visible text (F005).** Canonical visible text: concatenate adjacent text nodes with NO inserted separator; `<br>` and block boundaries (`p`, `li`, `blockquote`) contribute one `\n`; then collapse whitespace runs to one space, trim. Same rule in Go and the client counter. Tests add `<p>a<strong>b</strong>c</p>` = 3, inline link/mention boundaries, formatted 1,000/1,001.
- **N08 (F011).** ALG-001 missing-row branch returns 404 `kudo_not_found` (C03). Acceptance: nonexistent UUID for both Spam and Public.
- **N09 router contract (F002, F003).** F002 states route classes: CORS wraps the whole mux; PUBLIC: `GET /api/v1/events/current` (no JWT); IDENTITY-ONLY: `POST /api/v1/me/provision` (verified JWT, no profile required); PROFILE: all other `/api/v1/*` (JWT + existing profile); ADMIN: `/api/v1/admin/*` (PROFILE + `RequireAdmin`). F003 SC-006 runs against the assembled router.
- **N10 badge scope (F008, F009).** Per F007 D006 there is no hero badge in the profile header: remove the profile-header host/hover from F008; fix F009's explanation (notification still navigates to own profile, where the Sunner's kudo cards show badges).
- **N11 export streaming (F010).** Go writes headers only after the first page of rows is read successfully; a failure before that → 500 JSON. A failure after streaming starts aborts the connection (no trailer, no partial "success"). The browser downloads via `fetch` → blob and saves only after the full body completes; on abort it shows a retry. Test: failure after several rows → no truncated file saved, retry offered.
- **N12 stored replay (F008).** `secret_boxes.open_result jsonb` stores the full response `{boxId, icon, summary}` computed in the opening transaction; a replay with the same `Idempotency-Key` returns exactly that stored JSON. Current inventory is refreshed separately via `GET /api/v1/me/secret-boxes`. Test: open A → open B → retry A returns A's original result, nothing consumed.
